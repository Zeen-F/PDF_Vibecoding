# 本机索引搜索

正文、标题、单一笔记区与批注共用可重建的 SQLite FTS5 trigram 索引。搜索仍是忽略大小写的字面子串，保留既有换行归一化、摘要和最多 100 条结果规则。`gm/Id`、`[x_y]`、`100%` 与引号不会被当作搜索运算符。三字以上中文可以使用 trigram；一、二字查询使用 SQLite 的字面 `instr` 回退，无需分词器或网络服务。

每条正文结果保留实际 PDF 页码。批注结果另带稳定 `annotationId` 和归一化 `rects`；文献与搜索响应提供 `pdfSha256`，供阅读器核对来源身份。扫描件图片中没有提取到的文字仍不可全文搜索。

## 数据与恢复

- 原有 `documents`、`pages`、`annotations` 是来源；Obsidian 模式仍以管理 Markdown/PDF 为正式资料
- `search_*` 表、索引和触发器是可丢弃的派生缓存，不改变 schema 5，也不改写原 PDF、笔记或批注
- 初次启动建立缓存；旧库已有内容会在服务就绪前建立索引。初次构建需要额外时间和磁盘空间，后续打开复用缓存
- 原始表上的纯 SQL 触发器记录变化，下一次搜索事务性补齐。更新笔记、标题或单条批注只刷新对应条目，阅读位置更新不触发重建。旧版本正常写入同一数据库也会记录变化，无需自定义 SQLite 函数
- 外部 Markdown 读回沿用既有仓库刷新与冲突检查，之后再更新搜索缓存。内容 token 未改变时跳过条目重写，避免每次读取都删除再插入批注；文件读取和身份校验仍执行。搜索不绕过损坏文件、PDF 身份不匹配或保存冲突
- 需要手动刷新缓存时，在本机服务使用 `POST /api/search/rebuild`，请求 JSON 为 `{}`。该操作只重建派生条目，成功才提交；失败回滚。缓存结构缺失会在下次启动自动重建
- 回退旧程序不需要回退正式数据结构。标准备份仍须正常退出后复制完整文献库/知识库，或使用现有一致性备份流程；不要在运行时单独复制 SQLite 主文件

索引不是备份，也不用于修复正式记录损坏。遇到 SQLite 完整性错误，应按既有完整备份恢复流程处理，不删除正式数据重建空库。

## 查询策略与测量

索引命中候选后再次按归一化字面文本核验；Unicode 大小写采用和旧搜索相同的 JavaScript `toLowerCase()`。常见词先检查有序的有限前缀，足够 100 条时直接返回；否则继续全索引查询，避免为了返回前 100 条对全部常见命中排序。短词回退仍可能线性检查缓存，不能宣称任何库和任何查询都恒定耗时。

运行：

```sh
node scripts/benchmark-search.mjs
```

默认生成 160 篇、8,000 页、约 19.3 MB 的合成文本，在系统临时目录中比较旧版逐文献/页 JavaScript 扫描和新索引。脚本逐条断言结果完全一致，预热后取 9 轮中位数，同时报告首次构建和一次笔记增量更新时间；结束清理合成库。这是搜索引擎本身的计时，不包含 HTTP、PDF 导入、界面渲染或 Obsidian 仓库请求前的文件刷新。仓库刷新仍会读取管理文件，实际请求耗时可能受文件系统和同步状态影响。结果依赖机器、文件缓存、命中分布和实际文献，不代表正式资料测量。可指定 100–100,000 页，不会读取个人资料。

相关检查：`tests/search-index.test.mjs`（中英公式/标点、Unicode、短词、修改/删除/回滚、缓存恢复、排序/上限）及 `tests/search-api.test.mjs`（真实导入、笔记/区域批注、原图身份、重启、重建接口与来源限制）。
